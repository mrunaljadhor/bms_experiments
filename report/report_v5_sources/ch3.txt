=== CHAPTER 3 SYSTEM DEVELOPMENT & METHODOLOGY
## 3.1 System Block Diagram / Architecture
H3: 3.1.1 Layered architecture
iBMS has five layers (Fig. 3.1). The first layer, the data layer, converts BMS readings of pack voltage V, current I, maximum cell temperature T, cell-voltage difference ΔV_cell and SOC into 1 Hz time series, and adds synthetic discharge scenarios to widen the SOC range for training. The second layer, the model layer, trains the SOC estimator in TensorFlow/Keras and exports it to TensorFlow Lite. A Node.js service layer, the third layer, hosts the route-energy model (Section 4.5.2) and AMSA (Section 3.3.2); it queries the TomTom Routing API for the route with live traffic and OpenTopoData for SRTM 30 m elevations. A Next.js layer, the API layer, which is the fourth layer, exposes these functions as REST endpoints for a web dashboard, the user interface (UI), which is the final layer.
FIG: ../paper_figures/fig1_architecture.png | Fig. 3.1: Layered architecture of iBMS and data flow of a trip feasibility request (steps 1–5); dashed: offline training; dotted: planned online SOC feed
For a trip, when the rider enters the trip details, the dashboard sends the origin, destination, SOC, SOH and cruising speed to the feasibility endpoint, which returns the AMSA decision and its margins as a JSON response, which the dashboard displays. In the current prototype the SOC sent to AMSA is entered on the dashboard, because the LSTM is not yet connected to live BMS data from the vehicle. The stack is built in layers that are independent of each other, so each layer can be changed or moved without changing the others.

H3: 3.2.3 Dashboard functions
The dashboard provides an SOC control with a battery-status card; ECO and SPORT mode selection with four driving-profile levels that scale the consumption; the route-aware DTE and a charging recommendation; route planning on a map with traffic colouring and alternative routes; a route-physics panel (climb, grade, traffic-jam ratio, regeneration); the AMSA status and ECO-Lock banner; the SOH gauge and RUL estimate; analytics charts; and an intelligence suite with a conversational assistant, an explanation panel, the SOC-uncertainty card and a digital-twin simulator. A role toggle switches between the User view and the Analyst view.
## 3.3 Flowchart / Algorithm
H3: 3.3.1 SOC estimation and uncertainty pipeline
FIG: figures/fig_soc_flow.png | Fig. 3.4: SOC estimation and uncertainty pipeline
In the pipeline of Fig. 3.4, the BMS readings are interpolated to 1 Hz (synthetic full discharges are added for training) and cut into windows of 50 samples of voltage, current and temperature that never cross session boundaries. The inputs are scaled with training-data statistics only, and the LSTM outputs the SOC at the last step of the window; the SOC itself is never an input. For the risk-aware decision, the network is run 30 times with dropout active: the mean μ is the estimate, the standard deviation σ the uncertainty, and a conformal factor q gives the lower bound SOC_lb = μ − qσ, which the true SOC exceeds with 95 % confidence.
H3: 3.3.2 Route-level AMSA
FIG: figures/fig_amsa_flow.png | Fig. 3.5: Flowchart of the route-level Adaptive Mode Switching Algorithm
The AMSA of [14] switches modes while riding, using the instantaneous slope, but on a long slope this is already too late, because if the energy is not there beforehand, no switching on the way can save the trip. The modification done here is that AMSA (Fig. 3.5) turns the real-time mode selection of [14] into a pre-trip check per leg. Each leg length d_i is compared with the ECO and SPORT DTE at the SOC expected at the start of the leg. The leg is SAFE if reachable in SPORT mode (manual control), CRITICAL if reachable only in ECO mode (ECO-Lock enforced) and IMPOSSIBLE otherwise (charging stop required). The SOC at the start of the next leg follows Eq. (4.8) and is reset to 100 % after a charging stop.
- Input: legs $d_1, \dots, d_n$; initial SOC (minus the uncertainty margin in risk-aware mode); SOH; speed; route features.
- For each leg $i$: compute $DTE_{\mathrm{ECO}}(SOC_i)$ and $DTE_{\mathrm{SPORT}}(SOC_i)$ with Eqs. (4.4)–(4.7).
- If $d_i > DTE_{\mathrm{ECO}}$: IMPOSSIBLE, CHARGE_REQUIRED; stop.
- Else if $d_i > DTE_{\mathrm{SPORT}}$: CRITICAL, FORCE_ECO_MODE (SPORT disabled).
- Else: SAFE, MANUAL_MODE.
- Update $SOC_{i+1}$ with Eq. (4.8), or set it to 100 % after a charging stop.
Since DTE is proportional to SOC, single-leg thresholds are analytic (Eq. (4.8)). In risk-aware mode, the model is evaluated at SOC_lb instead of the point estimate, so an overestimated SOC cannot turn an infeasible trip into an accepted one; the endpoint takes the margin μ − SOC_lb as an input. Following the 40 % threshold below which [14] prefers ECO mode, the dashboard also disables SPORT mode below 40 % SOC. ECO-Lock is issued as a software command at the rider interface; torque limiting through the vehicle control unit (VCU) is planned.

## 3.5 Challenges and Complexities
- No road data: the vehicle could only be tested on a stand, and each session covers a small SOC range. Synthetic full discharges were added for training, the public CALCE data were used for a full-range test, and consumption was calibrated from the rated range.
- Sparse readings: the BMS app showed values only every ≈ 30 s, transcribed from screen recordings. They were interpolated to 1 Hz with small added noise.
- Data leakage: the first LSTM used the SOC as an input and an early comparison scored it against its own output. Both were discarded; the final model never sees the SOC and data are split by scenario and session.
- Choice of baselines: on the field data a constant predictor (1.22 %) matched the fine-tuned LSTM (1.24 %), so the field data cannot rank estimators and tracking was evaluated on CALCE.
- Flat LiFePO4 voltage curve: a simple EKF reached only 10.4 % on CALCE; an RC model with measured OCV (0.96 %) gave a fair baseline.
- Elevation bug: the backend requested an elevation dataset the public API does not offer, so every route was flat; it was switched to SRTM 30 m with at most 100 points per request.
